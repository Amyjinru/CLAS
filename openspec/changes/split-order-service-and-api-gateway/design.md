## Context

W2-ORDER-01 与 W2-GATEWAY-01 共同将 CLAS 从单体演进为可验证的服务化运行形态。当前 `OrderController` 与 `OrderService` 同时直接依赖商品、商家、购物车、地址、支付、配送、通知与评价领域的 Mapper/Service；`docs/microservice-design.md` 已规定订单表的唯一主写权、网关职责和公开路径兼容规则，但尚未有多模块工程、服务发现或网关实现。

相关参与方是订单、商品目录、商家、支付、配送服务的负责人，以及保持前端兼容的调用方。W2-CATALOG-01、W2-MERCHANT-01 与 W2-ARCH-01 是订单服务完成端到端验收的显式依赖。

## Goals / Non-Goals

**Goals:**

- 建立独立的订单履约服务，拥有订单相关表的唯一写入权、独立构建入口、容器镜像、健康检查与测试。
- 以内部 HTTP 契约代替订单服务对商品、商家、支付和配送领域表的直接访问，并在订单库中固化创建时所需快照。
- 让网关在不改变前端 `/api/**` 调用的前提下，路由至少三个业务服务，统一完成 JWT、请求 ID、限流和故障响应。
- 为同步调用和异步状态协同建立超时、幂等、可观测与可回滚的最小闭环。

**Non-Goals:**

- 不在本次将全部十二个领域都拆成服务，也不替换真实支付、短信、地图服务或实现完整消息队列。
- 不允许以共享数据库、跨服务 SQL 或分布式事务作为临时实现。
- 不对现有前端页面或公开 API 作破坏性改版；旧单体只在灰度/回退阶段保留兼容职责。

## Decisions

### 1. 采用 Maven 多模块单仓工程与独立 Spring Boot 进程

新增父 POM，并建立 `order-service`、`api-gateway` 以及由 W2-ARCH-01 提供的 `catalog-service`、`merchant-service` 模块。每个服务独立监听端口、构建镜像、执行测试和暴露 `/actuator/health` 或等价健康端点；Docker Compose 与 Kubernetes 均以服务名寻址。

选择单仓多模块而非立即拆分多个仓库，因为课程周期短、需要通过同一提交和 CI 串联证据；相较继续在单体内做包级划分，该方案可实际证明独立构建和部署。

### 2. 订单服务拥有订单写模型，并保存跨域快照

订单服务仅写 `orders`、`order_item`、`order_lifecycle_event`、`order_refund_dispute`。下单时先调用商品目录的 `/internal/catalog/v1/**` 获取可售商品、价格与库存校验结果，调用商家内部接口获取营业/配送状态；在本地事务中保存商品名称、单价、商家名称和配送快照。订单读取不得再为展示而访问商品或商家表。

库存扣减由商品目录的受控命令完成，失败即不创建订单；购物车清理由购物车服务命令完成，并允许失败后按幂等键重试。该方式避免共享写表；替代方案是保留单库直接 Mapper 访问，但不满足任务卡的数据隔离要求。

### 3. 用 HTTP 契约加幂等事件入口处理支付与配送协同

订单服务向支付、配送发布带 `eventId`、`orderId`、`version` 的命令/事件；支付成功、骑手送达等回调进入订单服务的内部受保护端点。服务对 `(source, eventId)` 去重，并仅允许合法状态转换；调用设定连接和读取超时，调用失败返回可重试的受控错误且保留关联请求 ID。

课程实现先使用本地 Outbox 表或可重放事件记录，后续再接入 MQ；不使用同步分布式事务，以避免部分成功时无法恢复。

### 4. 网关统一处理入口横切能力，业务服务保留资源授权

API 网关采用 Spring Cloud Gateway 和服务发现（本地 Compose/Kubernetes 使用稳定服务名；若引入注册中心，作为同一发现抽象的实现）。网关路由 `/api/order/**`、`/api/product/**`、`/api/merchant/**` 到对应服务，校验并透传 Bearer JWT，生成或透传 `X-Request-Id`，并将其写入响应和结构化日志。

网关采用令牌桶限流并对超时、不可达和熔断打开统一返回 `503` 与请求 ID；公开健康端点不受认证限制。业务服务仍必须按角色和资源归属再次授权，不能把网关视为唯一安全边界。

### 5. 以兼容路由、影子验证和可回退发布切换

前端继续请求现有 `/api/**`。先部署新服务与网关、运行内部契约/API 回归和受控故障实验，再将 Ingress `/api` 指向网关。发生验证失败时，将 Ingress 切回已记录 SHA 的单体后端，并保留网关和服务日志；不迁移或删除订单数据，直到备份、校验与回归都通过。

## Risks / Trade-offs

- [商品、商家服务尚未交付内部契约] → 将其列为启动门；先用契约桩完成订单服务测试，联调只在真实服务就绪后进行。
- [订单逻辑当前直接读取多个领域表] → 逐个建立契约测试和快照字段迁移，禁止一次性删除单体实现。
- [JWT 配置在新服务间不一致] → 共享仅包含验证公钥/密钥引用和统一 claims 约定的安全配置，CI 增加有效、过期和越权令牌测试。
- [服务发现或网关配置错误造成全部入口不可用] → 每次变更前后运行路由/健康检查，保留单体 Ingress 回退清单。
- [同步调用放大延迟或故障] → 设定短超时、限流/熔断和可观测请求 ID，读操作仅在可安全降级时返回备用结果。

## Migration Plan

1. 锁定服务模块、端口、健康检查、私有 schema、表 owner 与内部契约；确认 #36、#37、#38 的接口基线。
2. 提取订单领域模型和迁移脚本，先以契约桩完成独立构建、单元和集成测试。
3. 部署订单、商品目录、商家服务以及网关，运行订单创建、退款、非法状态跃迁、重复事件和公开路径兼容回归。
4. 执行一次商品/商家依赖超时或停止实例的受控故障实验，记录请求 ID、日志、健康检查和恢复步骤。
5. 将 `/api` Ingress 切至网关；若任一健康检查或回归失败，立即切回先前单体 SHA，并依据日志修复后重试。

## Open Questions

- #36、#37、#38 的模块目录、端口、内部认证方式和可联调时间尚未提交，需在实施前由对应负责人冻结。
- 支付、配送服务在本阶段采用同步内部回调还是 Outbox 轮询，需要与其负责人确认事件载荷、重试上限与失败补偿责任。
- 当前 Kubernetes 单机环境是否可提供独立注册中心；若不可用，使用 Kubernetes DNS/Compose 服务名作为本阶段服务发现实现。
