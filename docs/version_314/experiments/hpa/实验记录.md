# clas-catalog HPA 与压力测试实验记录

## 结论

- **HPA 扩缩容机制：通过。** CPU 从 3% 升至 271%/314% 后，目标副本数从 1 增至 2、再增至 3；停止负载并恢复稳定后，HPA 自动从 2 缩回 1。
- **原定 100 VU 容量压测：未通过，按安全规则提前终止。** 单节点在 10 VU 阶段扩容并同时启动多个 Java Pod 时发生控制面 TLS handshake timeout、Metrics API 暂时不可用以及多个工作负载探针超时。没有继续进入 50/100 VU 阶段。
- **最终恢复：通过。** catalog 回到 1/1，HPA 为 `1–4`、CPU 目标 60%，九个 Deployment 全部 Available；公网健康、商品列表及五个微服务集群内健康检查均为 HTTP 200。

## 失败现象与根因判断

HPA 自身正确响应 CPU 指标；失败发生在单节点容量层。三个 catalog 实例启动时，单实例 CPU 分别约为 232m、273m、329m，叠加其余五个 Java 服务、MySQL、k3s 控制面和容器运行时后，主机 load average 达到 14.95。随后出现：

- k3s API `TLS handshake timeout`；
- Metrics API 暂时不可用；
- catalog 一度 0/3 Ready；
- MySQL、order、frontend 被存活探针重启；
- 多个服务 readiness/liveness probe 超时；
- 公网健康短时连接失败。

因此当前 2 vCPU/3.5 GiB 单节点不具备执行既定最高 100 VU、多 Java Pod 并发启动的容量余量。正式重测前至少应增加节点 CPU/内存，或将业务工作负载与控制平面分离；不能仅通过提高探针超时掩盖资源不足。

## 恢复与后续复测条件

发现控制面超时后立即停止 k6，删除 HPA、将 catalog 限制为 1 个副本，等待全部 Deployment 恢复，再重新应用 HPA。最终节点 CPU 约 16%–27%、内存 78%，HPA 自动回到 1 个副本。
