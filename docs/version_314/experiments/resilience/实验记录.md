# clas-catalog 依赖故障注入与恢复实验记录

## 结论

**通过。** 在远程单节点 k3s 集群中主动停止 `clas-catalog` 后，订单预览从 HTTP 200 变为受控 HTTP 503，IAM、merchant、order、compat 服务保持健康；恢复 catalog 和 HPA 后，订单预览重新返回 HTTP 200。

## 环境与口径

- 实验时间：2026-09-02 23:23–23:25（Asia/Shanghai）
- 目标：`http://8.141.112.182`
- 集群：k3s `v1.36.3+k3s1`，单节点、2 vCPU、约 3.5 GiB 内存
- 线上镜像提交：`e67b1f7d99ba841d9d294538a4f3ed1aaacdf315`
- 命名空间：`clas`
- 故障对象：Deployment/HPA `clas-catalog`
- 订单预览商户：`merchantId=1`。预检发现商户 3 在订单域返回业务 400，故不用于依赖故障实验。
- 测试账号令牌只存在于进程环境，未写入证据或仓库。

## 最终有效运行

| 时间 | 阶段 | 结果 |
|---|---|---|
| 23:23:01 | 正常订单预览 | HTTP 200 |
| 23:23:09 | catalog 缩容为 0 后订单预览 | HTTP 503，`UPSTREAM_UNAVAILABLE`，提示“商品目录服务暂不可用，请稍后重试” |
| 故障期间 | IAM、merchant、order、compat 健康检查 | 全部 HTTP 200 |

| 23:24:58 | 脚本结束 | exit 0，总时长 117 秒 |

恢复后的集群内 catalog 健康检查通过，恢复阶段五个微服务健康检查全部通过。最终公网、商品列表和五服务集群内健康检查均为 HTTP 200。

## 发现并修复的问题

第一次运行被保留为无效运行：catalog Pod 已恢复，但 HPA 没有重建，并且恢复后第一次公网请求因传播延迟得到 503。原因与修复如下：

1. `recover-catalog.sh` 使用 JSONPath 读取含点号的 annotation key，实际得到空值；改用 Go template 的 `index` 读取完整 key，保证 `hpa-was-present=true` 能被识别。
2. 恢复脚本只确认集群内 catalog 健康，编排脚本随后立即请求公网；改为最多 12 次、间隔 5 秒等待恢复请求返回 200。

修复通过 `bash -n` 和完整故障—恢复重跑验证。
