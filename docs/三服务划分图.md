# CLAS 三业务微服务 + compat 划分图

> 状态：当前实现（2026-09-01）。至少 3 个核心业务微服务；`clas-compat` 已经主写骑手、公告和沟通数据，因此按运行职责应视为**第四个业务服务**，而非纯只读聚合层。
> 网关：前端 Nginx 按路径反代（不算业务微服务）。

## 1. 划分原则

- **最大归属**：概念上归属清晰的模块并入 iam / catalog / order。
- **不硬塞**：骑手配送、运营与沟通保持为独立 compat 服务；后续可继续拆为配送、沟通、运营服务。
- **一表一主写**：其他服务只走 HTTP 内部接口，禁止跨库 JOIN。

## 2. 架构图

```mermaid

    NGX --> ORD[clas-order<br/>交易与评价]

    ORD -->|HTTP| CAT

    ORD -->|HTTP| CMP
    CAT -->|HTTP| IAM
    CMP -->|HTTP 受控查询| IAM
    CMP -->|HTTP 受控查询| CAT
    CMP -->|HTTP 受控查询| ORD

    IAM --- DB[(MySQL clas)]
    CAT --- DB
    ORD --- DB
    CMP --- DB

    IAM --- R[(Redis)]
```

## 3. 三个业务微服务职责

| 服务 | 端口 | 负责业务 | 为何独立 |
| --- | --- | --- | --- |
| **clas-iam** | 8081 | 注册登录、资料、地址、收藏、银行卡、站内通知、角色申请、用户侧处罚/申诉 | 身份是全系统入口，与交易解耦 |
| **clas-catalog** | 8082 | 商家入驻/审核、商品、**团购发布**、**服务预约**、商品/商家图片 | 供给与读多写少的目录域 |
| **clas-order** | 8083 | 购物车、订单、支付、退款、**团购购买/核销**、**优惠券**、**订单评价** | 核心交易写路径与状态机 |

## 4. compat 职责（第四业务服务）

| 模块 | 说明 |
| --- | --- |
| 骑手 / 配送 UC16 | 独立域，表多，与 order 双向联动；不强行并入 order |
| `/api/admin` | 跨服务聚合、导出；聚合数据必须逐步改为内部 API 或只读投影 |
| `/api/announcement` | 平台公告 |
| 沟通、公告与骑手运营 | 主写其归属表；不得被描述为纯兼容层 |
