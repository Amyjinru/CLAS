# CLAS README 重写设计

## 目标

基于当前仓库代码重写根目录 `README.md`，使其同时满足两类读者：

- 课程答辩、项目展示人员能够快速理解项目定位、业务范围和技术亮点。
- 新开发者能够准确完成环境配置、数据库初始化、本地启动、测试和部署。

README 中的事实以当前代码、配置文件、数据库脚本和部署脚本为准，不沿用已经过时的阶段性描述。

## 文档结构

README 采用“双用途型”结构：

1. 项目名称与一句话定位。
2. 项目概览与核心业务闭环。
3. 用户端、商家端、管理端和平台能力的功能矩阵。
4. 技术栈与系统架构概览。
5. 项目目录结构。
6. 环境要求与快速启动。
7. 后端、前端和第三方服务配置。
8. 数据库初始化与增量迁移。
9. 演示账号与关键业务约定。
10. 测试、构建与 Linux 部署。
11. 项目文档索引和维护约定。

## 内容原则

- 功能描述从前端路由、后端 Controller/Service 和数据库结构交叉验证。
- 依赖版本从 `backend/pom.xml` 和 `frontend/package.json` 提取。
- 端口、代理和环境变量从应用配置及 Vite 配置提取。
- 演示账号从 `database/schema.sql` 提取。
- 数据库规模按当前 `schema.sql` 中的建表语句统计。
- 启动、测试、构建和部署命令必须与仓库现有脚本一致。
- README 保持入口文档的可读性，不逐项罗列全部 REST API；详细设计、测试和运维内容通过链接指向 `docs/`、`tests/` 和 `scripts/server/README.md`。

## 表达方式

- 全文使用中文，技术名词和命令保留原始英文。
- 开头优先呈现项目价值和业务闭环，随后再进入工程信息。
- 使用表格呈现功能矩阵、技术栈、配置项和演示账号。
- 使用短代码块提供可直接执行的命令。
- 避免宣传性夸张描述，不声称代码中无法验证的能力。

## 验证标准

- README 中不存在旧的“MVP 极简框架”定位。
- 功能、表数量、依赖、端口、配置和账号与当前代码一致。
- 新开发者能够仅根据 README 完成本地初始化和启动。
- 文档能够清晰展示普通订单、团购、预约、商家运营和平台治理等主要能力。
- Markdown 标题层级、表格、代码块和仓库路径均有效。
