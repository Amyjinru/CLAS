### 1.2 统一 API 响应

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "timestamp": 1781179200000,
  "requestId": "trace-123",
  "errorCode": null
}
```

失败响应通过真实 HTTP 状态和稳定 `errorCode` 区分认证、授权、校验、资源不存在、状态冲突和系统错误。

### 1.3 认证和归属

1. 前端 Axios 请求拦截器从本地会话取 JWT，添加 `Authorization: Bearer <token>`。
2. 后端认证拦截器解析 JWT，将用户 ID 和角色写入 `UserContext`。
3. Controller 使用 `@RequireRole` 做角色检查。
4. Service 使用 `UserContext.getUserId()` 或 `MerchantService.getCurrentMerchantId()` 做数据归属检查。

### 2.2 收藏处理逻辑

```text
add(merchantId):
  1. 按 merchantId 查询商家；不存在则抛出“商家不存在”。
  2. 从 UserContext 取得 userId。
  3. 查询 userId + merchantId 收藏关系。
  4. 已存在则直接返回，保证重复收藏幂等。
  5. 不存在则写入 favorite 并返回。

remove(merchantId):
  按当前 userId + merchantId 删除；不存在时删除数为 0，最终仍为未收藏。

mine():
  1. 按当前 userId 查询收藏，ID 倒序。
  2. 提取 merchantId 列表。
  3. 批量返回商家；无收藏时返回空列表。
```

### 2.3 通知处理逻辑

```text
send(NotificationTarget):
  将接收人、标题、正文、类型、目标资源及 targetPath 写入 notification，readFlag=false。

mine():
  1. 仅查询当前用户。
  2. readFlag 升序（未读优先），ID 倒序（最新优先）。
  3. 对缺少结构化目标的旧通知尝试回填。
  4. 返回列表。

markRead(id):
  仅当通知存在且 userId 等于当前用户时更新 readFlag=true。

deleteOne(id):
  通知不存在或不属于当前用户时抛出“通知不存在或无权删除”；否则删除。

markAllRead()/deleteAllMine():
  只处理当前用户范围。
```

### 2.4 历史通知目标回填

| 目标类型 | 解析依据 | 归属验证 | 目标路径 |
| --- | --- | --- | --- |
| ORDER | 历史标题/正文中的订单 ID | `order.user_id == notification.user_id` | `/order/{orderId}` |
| REVIEW | 订单 ID 查找该用户评价 | `review.user_id == notification.user_id` | `/review/{orderId}?reviewId={reviewId}` |
| DEAL_ORDER | 券码或通知时间附近的本人团购订单 | `deal_order.user_id == notification.user_id` | `/deal-order/{id}` |
| BOOKING | 通知标题和服务名称 | 用户本人预约或其商家预约 | `/bookings?...` 或 `/merchant/bookings?...` |

客户端在目标后追加 `from=notifications`，使详情页能够返回通知中心。

### 3.2 入驻处理流程

```text
register(request, loggedInUserId):
  1. 规范化并校验 contactPhone。
  2. 如果未登录：
     a. 校验 accountPhone 和 register 验证码。
     b. 要求密码；新账号还要求 username、密码强度和确认密码。
     c. 新建 MERCHANT 账号，或校验既有账号密码并把 USER 升级为 MERCHANT。
  3. 如果已登录：查询账号；USER 升级为 MERCHANT。
  4. 校验该用户没有其他商家。
  5. 校验店名唯一、联系电话唯一。
  6. 校验地图经纬度存在，规范配送范围。
  7. 创建 merchant：
     status=PENDING
     manualClosed=false
     businessHours=09:00-21:00
     deliveryFee/minOrderPrice/averagePrice=0
     score=0.00
  8. 返回 MerchantResponse。
```

该方法为事务方法，避免账号角色变化和商家创建出现部分成功。

### 3.3 审核处理流程

```text
audit(merchantId, request, adminId):
  1. 查询商家；不存在则失败。
  2. 读取 oldStatus 和 request.status。
  3. validateStatusTransition(oldStatus, newStatus)。
  4. 更新 merchant.status；提供备注时更新 adminRemarks。
  5. 插入 merchant_audit_log：merchantId/adminId/old/new/remarks。
  6. 返回更新后的 MerchantResponse。
```

审核方法使用事务，状态更新和日志写入共同提交或回滚。

### 3.4 状态机规则

| 当前状态 | 目标状态 | 结果 |
| --- | --- | --- |
| 任意状态 | 相同状态 | 允许，可更新备注 |
| PENDING | APPROVED/BLOCKED | 允许 |
| APPROVED | OPEN/CLOSED/BLOCKED | 允许 |
| OPEN | CLOSED/BLOCKED | 允许 |
| CLOSED | OPEN/BLOCKED | 允许 |
| BLOCKED | APPROVED/CLOSED/OPEN | 允许 |
| 其他组合 | — | 抛出包含允许目标的业务错误 |

### 3.5 API 设计

| 方法 | 路径 | 角色 | 主要输入 | 输出 |
| --- | --- | --- | --- | --- |
| POST | `/api/merchant/register/send-code` | 公开 | `phone` | 验证码已发送 |
| POST | `/api/merchant/register` | 游客/已登录 | `MerchantRegisterRequest` | PENDING 商家 |
| GET | `/api/merchant/my` | 已登录商家账号 | 无 | 本人商家 |
| GET | `/api/merchant/my/audit-status` | MERCHANT | 无 | `status`, `adminRemarks`, `auditTimeline` |
| GET | `/api/merchant/admin/list` | ADMIN | 无 | 全部商家 |
| POST | `/api/merchant/admin/audit/{id}` | ADMIN | `status`, `remarks` | 更新后商家 |
| GET | `/api/merchant/admin/audit-logs/{id}` | ADMIN | 商家 ID | 审核日志倒序列表 |

### 3.6 数据设计

`merchant` 与本用例相关的字段：`id`, `user_id`, `merchant_name`, `phone`, `category`, `address`, `longitude`, `latitude`, `status`, `manual_closed`, `admin_remarks`, `bank_account`, `settlement_cycle`, `created_at`, `updated_at`。

`merchant_audit_log`：

| 字段 | 说明 |
| --- | --- |
| `merchant_id` | 被审核商家 |
| `admin_id` | 审核管理员账号 |
| `old_status` | 审核前状态 |
| `new_status` | 审核后状态 |
| `remarks` | 审核依据/备注 |
| `created_at` | 操作时间 |

### 3.7 权限和异常

| 场景 | 处理 |
| --- | --- |
| 游客验证码错误 | 拒绝入驻 |
| 新账号缺少密码/展示名 | 拒绝入驻 |
| 密码错误、账号禁用 | 拒绝复用账号 |
| 一人多店 | “每个用户只能入驻一个商家” |

### 4.2 当前商家解析

```text
getCurrentMerchantId():
  1. 从 UserContext 取 userId；为空则“未登录，请先登录”。
  2. 按 merchant.user_id 查询商家。
  3. 不存在则“当前用户未入驻为商家”。
  4. 返回 merchant.id。
```

所有规范商品写接口忽略客户端商家归属，统一使用该方法。

### 4.3 店铺资料更新

```text
updateMyProfile(request):
  1. 取得当前商家和原联系电话。
  2. 规范并校验店名、地址、新电话、银行账号。
  3. 校验地图坐标。
  4. 如果电话变化：校验新电话收到的 merchant-phone-change 验证码。
  5. 如果银行账号变化：要求 9~25 位数字，并校验原电话收到的 merchant-bank-change 验证码。
  6. 电话变化时检查其他商家未占用。
  7. 校验配送范围和营业时间。
  8. 更新 merchant 并返回最新响应。
```

营业时间：缺省时保留原值或使用 `09:00-21:00`；指定值必须能被 `LocalTime` 解析。跨午夜营业时间由业务判断支持。

### 4.4 手动打烊

```text
toggleManualClosed():
  1. 取得当前商家。
  2. merchant.status 必须为 OPEN。
  3. manualClosed = !manualClosed。
  4. 更新并返回最新商家。
```

用户购买团购时还会结合 `manualClosed` 和 `businessHours` 判断商家当前是否可营业。

### 4.5 分类处理

| 操作 | 规则 |
| --- | --- |
| 查询 | 按当前商家、`sortOrder` 和 ID 升序 |
| 创建 | 名称非空；同店名称唯一；默认排序 0 |
| 更新 | 分类必须属于当前商家；新名称不能与本店其他分类重复 |
| 删除 | 分类必须属于当前商家；先将相关商品 `categoryId=null`，再删除分类 |

### 4.6 商品处理

| 操作 | 规则 |
| --- | --- |
| 创建 | 归属当前商家；分类必须属于本店；初始 `ON_SALE` |
| 编辑 | 商品必须存在且属于当前商家；按非空字段更新 |
| 状态更新 | 仅允许 `ON_SALE`、`OFF_SALE` |
| 删除 | 商品必须属于当前商家；状态改为 `DELETED` |
| 商家列表 | 当前商家范围，排除 `DELETED`，支持分页/关键字/分类 |
| 用户列表 | 指定商家范围，仅 `ON_SALE` |
| 用户分组 | 仅 `ON_SALE`，按分类分组，移除空分组 |
| 后续处理 | 创建、编辑、状态变化、删除后刷新店铺人均价格 |

### 5.2 普通优惠券领取

```text
listClaimable(userId):
  1. 查询 ACTIVE 且当前时间在有效期内的 coupon。
  2. 查询用户已领取 couponId。
  3. 排除已领取和 totalLimit 已满的券。

claim(userId, couponId):
  1. requireActiveCoupon。
  2. 检查用户未领取过。
  3. 条件更新 claimed_count，只有未满时增加。
  4. 插入 user_coupon(status=UNUSED, claimedAt=now)。
```

### 5.3 普通优惠券结算

可用性检查：

- 用户券属于当前用户且状态为 `UNUSED`。
- 券定义为 `ACTIVE`，当前时间在有效期内。
- 券为平台券或 `merchantId` 等于当前订单商家。
- 订单商品小计不低于 `minOrderAmount`。

折扣计算：

- `FIXED`：`min(max(discountAmount, 0), subtotal)`。
- `PERCENT`：按折扣百分比计算，并限制结果不超过小计。

生命周期：

```text
create order:
  reserveForOrder(userCouponId, userId, orderId)
  条件：当前状态 UNUSED 且属于 userId
  结果：RESERVED + order_id

cancel/timeout:
  releaseForOrder(userCouponId)
  结果：UNUSED + order_id 清空

payment success:
  markUsed(userCouponId, orderId)
  条件：RESERVED 且 order_id 匹配
  结果：USED + used_at
```

### 5.4 团购购买与支付

```text
buy(dealId):
  1. 检查用户没有平台使用限制。
  2. 团购存在且状态 ON_SALE。
  3. 商家存在、未手动打烊且在营业时间内。
  4. 团购显示库存大于 0。
  5. 创建 deal_order：
     status=PENDING_PAYMENT
     voucherCode=PEND-随机串
     payAmount=dealPrice
  6. 尝试发送待支付通知；通知失败不回滚订单。

payDealOrder(id, userId, payMethod):
  1. 校验订单属于当前用户。
  2. 仅 PENDING_PAYMENT 可支付；已 UNUSED/USED 时返回已有支付状态。
  3. 再次检查团购存在且 ON_SALE。
  4. FAIL_MOCK 返回 FAILED，订单和库存不变。
  5. 模拟支付延迟。
  6. GroupDealMapper.deductStock 条件扣库存；0 行表示库存不足。
  7. 订单更新为 UNUSED，券码改为 CLAS-随机串，设置 paidTime 和 expireTime。
  8. 尝试发送购买成功通知。
```

### 5.5 团购券核销

```text
redeem(voucherCode):
  1. 券码非空并能查询到 deal_order。
  2. 当前 merchantId 必须等于 order.merchantId。
  3. 刷新过期状态；EXPIRED 拒绝。
  4. 仅 UNUSED 可核销。
  5. 更新 order.status=USED、usedTime=now。
  6. 插入 deal_redeem_log。
  7. 发送核销成功通知。
```

### 5.6 团购券过期与退款

`refreshExpiredStatus` 在查询/核销等入口发现 `UNUSED` 且 `expireTime < now` 时更新为 `EXPIRED`。

退款要求订单属于当前用户、状态为 `UNUSED` 且未过期。成功时 `GroupDealMapper.restoreStock` 恢复库存，订单转为 `REFUNDED` 并通知用户。
