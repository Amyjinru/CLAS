## 1. 文档目的

本文档集中说明 UC05–UC08 的参与者、触发条件、前置条件、主成功流程、备选/异常流程、后置条件和可验证结果。相关需求见 [02-需求说明书.md](02-需求说明书.md)，概要设计见 [03-概要设计说明书.md](03-概要设计说明书.md)，详细设计、代码与测试映射见 [04-详细设计说明书.md](04-详细设计说明书.md)。

## 2. 参与者与公共约束

| 参与者 | 说明 |
| --- | --- |
| 用户（USER） | 浏览商家、收藏、接收通知、领取优惠券、购买及使用团购券 |
| 商家（MERCHANT） | 维护店铺和商品、查看审核进度、核销本店团购券 |
| 申请人 | 已登录用户或尚未登录、需要同步创建账号的入驻申请者 |
| 管理员（ADMIN） | 审核商家、维护商家平台状态、查看审核日志 |
| 外部/支撑服务 | MySQL、Redis 验证码存储、模拟支付、通知服务 |

公共约束：

- 私有操作使用 JWT Bearer Token 鉴权。
- 服务端以当前认证身份判断数据归属，不信任客户端自行传入的用户或商家身份。
- 金额字段以“分”为单位存储和传输，前端按“元”展示。
- 当前阶段使用模拟支付，不连接真实支付渠道。
- 本文档描述当前代码行为；“可验证”不等同于“本轮已测试通过”。

## 3. UC05 用户收藏商家并接收业务通知

### 3.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC05 |
| 用例名称 | 用户收藏商家并接收业务通知 |
| 主要参与者 | 用户 |
| 协作参与者 | 商家、订单/团购/预约/评价等业务服务 |
| 触发条件 | 用户点击收藏或取消收藏；业务状态变化产生面向用户的通知 |
| 前置条件 | 用户已登录且角色为 USER；收藏目标商家存在；通知事件已由业务服务产生 |
| 成功后置条件 | 收藏关系与界面一致；业务通知归属于当前用户，并可查看、已读、删除和安全跳转 |
| 最低保证 | 失败操作不新增重复收藏、不修改其他用户通知、不执行任意外部或非白名单跳转 |

### 3.2 主成功流程

1. `UC05-F01` 用户进入商家详情页并点击“收藏”。
2. `UC05-F02` 系统根据当前登录用户和商家 ID 查询收藏关系。
3. `UC05-F03` 系统创建唯一收藏关系，并向前端返回收藏结果。
4. `UC05-F04` 用户进入个人中心，系统返回当前用户收藏的商家列表。
5. `UC05-F05` 订单、团购、预约或评价状态变化时，相应业务服务写入结构化通知。
6. `UC05-F06` 用户进入通知中心，系统按“未读优先、时间倒序”返回本人通知。
7. `UC05-F07` 用户点击可跳转通知，客户端先将通知标记为已读。
8. `UC05-F08` 客户端将通知解析为受控站内目标，并进入订单、评价、团购订单或预约详情。
9. `UC05-F09` 用户可取消收藏、全部已读、删除单条通知或清空本人通知。

### 3.3 备选或异常流程

| 编号 | 条件 | 系统处理 |
| --- | --- | --- |
| `UC05-A01` | 重复收藏同一商家 | 返回已有收藏关系，不新增重复记录 |
| `UC05-A02` | 收藏目标商家不存在 | 拒绝操作，返回“商家不存在” |
| `UC05-A03` | 取消未收藏商家 | 保持无收藏状态，操作幂等完成 |
| `UC05-A04` | 用户尝试删除他人通知 | 拒绝删除，目标通知保持不变 |
| `UC05-A05` | 用户尝试将他人通知标记已读 | 不修改目标通知 |
| `UC05-A06` | 历史通知缺少结构化目标 | 仅在能解析并验证资源归属时回填目标 |
| `UC05-A07` | 通知不是已支持的业务类型 | 不执行任意路径跳转 |
| `UC05-A08` | 用户未登录或角色不符 | 返回 401 或 403，不暴露业务数据 |

### 3.4 可验证结果

- `UC05-V01` 同一 `user_id + merchant_id` 最多存在一条收藏记录。
- `UC05-V02` 收藏列表只包含当前用户的收藏商家。
- `UC05-V03` 通知列表只包含当前用户通知，未读项排在已读项之前。
- `UC05-V04` 已读、删除和批量操作不影响其他用户通知。
- `UC05-V05` 可跳转通知进入受控站内页面，并附加 `from=notifications` 上下文。
- `UC05-V06` 取消收藏后，个人中心和商家详情的收藏状态一致。

### 3.5 关联需求

`REQ-UC05-01`～`REQ-UC05-05`。

## 4. UC06 商家入驻申请与管理员审核开店

### 4.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC06 |
| 用例名称 | 商家入驻申请与管理员审核开店 |
| 主要参与者 | 申请人、管理员 |
| 协作参与者 | 用户账号服务、验证码存储、商家服务 |
| 触发条件 | 申请人提交入驻资料；管理员提交审核状态和备注 |
| 前置条件 | 游客已获取账号手机号验证码并填写账号资料，或申请人已登录；商家资料包含店名、联系电话、分类、地址和地图坐标；审核者为 ADMIN |
| 成功后置条件 | 新商家以 PENDING 保存；审核后状态和备注更新，并追加审核日志；进入 OPEN 后可营业 |
| 最低保证 | 非法申请不产生残缺商家；非法状态转换不改变状态且不写入成功审核日志 |

### 4.2 主成功流程

1. `UC06-F01` 申请人进入商家入驻页面并填写账号和店铺资料。
2. `UC06-F02` 游客获取账号手机号验证码；已登录用户沿用当前账号。
3. `UC06-F03` 申请人提交店名、联系电话、分类、地址、地图坐标及可选结算信息。
4. `UC06-F04` 系统校验验证码/账号、密码、店名、电话、坐标以及“一人一店”约束。
5. `UC06-F05` 系统必要时创建账号或将 USER 升级为 MERCHANT。
6. `UC06-F06` 系统创建状态为 `PENDING`、`manualClosed=false` 的商家。
7. `UC06-F07` 申请人进入审核进度页，查看状态、管理员备注和审核时间线。
8. `UC06-F08` 管理员进入审核管理页，查看商家详情并提交 `APPROVED` 和审核备注。
9. `UC06-F09` 系统校验状态转换，更新商家并写入一条审核日志。
10. `UC06-F10` 管理员将 `APPROVED` 商家更新为 `OPEN`，系统再次记录审核日志。

### 4.3 状态转换

| 当前状态 | 允许目标状态 |
| --- | --- |
| `PENDING` | `APPROVED`、`BLOCKED` |
| `APPROVED` | `OPEN`、`CLOSED`、`BLOCKED` |
| `OPEN` | `CLOSED`、`BLOCKED` |
| `CLOSED` | `OPEN`、`BLOCKED` |
| `BLOCKED` | `APPROVED`、`CLOSED`、`OPEN` |

同状态更新允许执行，用于补充或修改管理员备注。

### 4.4 备选或异常流程

| 编号 | 条件 | 系统处理 |
| --- | --- | --- |
| `UC06-A01` | 游客验证码错误 | 拒绝申请 |
| `UC06-A02` | 密码不符合规则或两次密码不一致 | 拒绝创建账号和商家 |
| `UC06-A03` | 已有账号密码错误或账号被禁用 | 拒绝申请 |
| `UC06-A04` | 申请人已经绑定商家 | 返回“一人一店”业务错误 |
| `UC06-A05` | 店名或联系电话重复 | 拒绝申请并说明冲突字段 |
| `UC06-A06` | 未选择合法地图位置 | 拒绝申请 |
| `UC06-A07` | 商家不存在 | 拒绝审核 |
| `UC06-A08` | 状态转换不合法 | 保持原状态，不新增成功日志 |
| `UC06-A09` | 非管理员调用审核接口 | 返回 403 |
| `UC06-A10` | 申请人尚未入驻却查询审核状态 | 返回“当前用户未入驻为商家” |

### 4.5 可验证结果

- `UC06-V01` 商家记录的 `user_id` 指向申请人的账号。
- `UC06-V02` 新商家状态为 `PENDING`，且 `manual_closed=false`。
- `UC06-V03` 成功审核后商家状态和管理员备注与提交内容一致。
- `UC06-V04` 每次成功审核都有包含商家、管理员、旧状态、新状态、备注和时间的日志。
- `UC06-V05` 非法状态转换前后数据不变，日志数量不增加。
- `UC06-V06` 申请人审核进度页和管理员审核详情展示一致。

### 4.6 关联需求

`REQ-UC06-01`～`REQ-UC06-04`。

## 5. UC07 商家维护店铺、商品与经营状态

### 5.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC07 |
| 用例名称 | 商家维护店铺、商品与经营状态 |
| 主要参与者 | 商家 |
| 协作参与者 | 验证码存储、图片上传、商品与分类服务 |
| 触发条件 | 商家修改店铺资料、切换临时打烊、维护分类或维护商品 |
| 前置条件 | 商家已登录且角色为 MERCHANT；账号已绑定商家；手动打烊要求平台状态为 OPEN |
| 成功后置条件 | 变更仅作用于当前商家；用户侧只展示 ON_SALE 商品；经营状态可被交易入口识别 |
| 最低保证 | 失败操作不修改其他商家资源；删除分类不删除商品；商品删除采用软删除 |

### 5.2 主成功流程

1. `UC07-F01` 商家进入工作台，系统从当前认证账号解析商家 ID。
2. `UC07-F02` 商家查看并修改店名、地址、地图位置、配送范围、营业时间和联系电话等资料。
3. `UC07-F03` 若联系电话或银行账号变化，系统要求对应验证码；校验通过后保存资料。
4. `UC07-F04` 状态为 `OPEN` 的商家切换 `manualClosed`，临时打烊或恢复营业。
5. `UC07-F05` 商家创建、重命名、排序或删除自己的商品分类。
6. `UC07-F06` 商家创建商品，系统默认设置为 `ON_SALE`。
7. `UC07-F07` 商家编辑商品资料及所属分类。
8. `UC07-F08` 商家在 `ON_SALE` 和 `OFF_SALE` 间切换商品状态，或将商品软删除为 `DELETED`。
9. `UC07-F09` 系统刷新商家人均价格。
10. `UC07-F10` 用户访问商家详情时，只能看到 `ON_SALE` 商品及有商品的分类分组。

### 5.3 备选或异常流程

| 编号 | 条件 | 系统处理 |
| --- | --- | --- |
| `UC07-A01` | 当前账号未绑定商家 | 拒绝管理操作 |
| `UC07-A02` | 非 OPEN 商家切换手动打烊 | 拒绝操作 |
| `UC07-A03` | 敏感字段变化但验证码无效 | 保留原资料并返回错误 |
| `UC07-A04` | 地图坐标缺失 | 拒绝更新 |
| `UC07-A05` | 配送范围不在 500～10000 米 | 拒绝更新 |
| `UC07-A06` | 营业时间不是 `HH:mm-HH:mm` | 拒绝更新 |
| `UC07-A07` | 分类名称为空或同店重名 | 拒绝创建/修改 |
| `UC07-A08` | 删除仍有商品的分类 | 商品保留，`category_id` 置空后删除分类 |
| `UC07-A09` | 商品状态不是 ON_SALE/OFF_SALE | 拒绝更新 |
| `UC07-A10` | 商家操作其他店铺商品/分类 | 拒绝操作，目标数据不变 |

### 5.4 可验证结果

- `UC07-V01` 所有写操作使用服务端解析的当前商家 ID。
- `UC07-V02` 敏感字段变化必须经过相应验证码；字段未变时无需验证码。
- `UC07-V03` 只有 `OPEN` 商家能够切换 `manual_closed`。
- `UC07-V04` 商家管理列表排除 `DELETED`，用户商品列表仅包含 `ON_SALE`。
- `UC07-V05` 删除分类后原商品仍存在并归入未分类。
- `UC07-V06` 跨商家写操作均失败。

### 5.5 关联需求

`REQ-UC07-01`～`REQ-UC07-05`。

## 6. UC08 用户购买、支付、使用团购券

### 6.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC08 |
| 用例名称 | 用户购买、支付、使用团购券 |
| 主要参与者 | 用户、商家 |
| 协作参与者 | 优惠券、购物车、订单、支付、团购、通知服务 |
| 触发条件 | 用户领取普通优惠券并下单，或购买团购套餐并支付；商家输入券码核销 |
| 前置条件 | 用户已登录；券有效且可领取/购买；普通订单满足使用门槛；团购商家可营业且库存充足；核销者为券所属商家 |
| 成功后置条件 | 普通券与订单状态一致；团购订单生成正式券码并可被本店核销；关键状态产生通知和审计记录 |
| 最低保证 | 支付失败不错误扣库存或核销优惠券；非法核销不改变券状态且不新增核销日志 |

### 6.2 主成功流程 A：普通优惠券下单

1. `UC08-F01` 用户查看可领取优惠券。
2. `UC08-F02` 用户领取有效且有额度的优惠券，系统创建状态为 `UNUSED` 的用户券。
3. `UC08-F03` 用户在结算预览中选择符合商家范围和最低金额的券。
4. `UC08-F04` 系统计算抵扣金额。
5. `UC08-F05` 创建订单时，系统将用户券原子更新为 `RESERVED` 并绑定订单 ID。
6. `UC08-F06` 用户支付订单，系统完成库存扣减和订单状态更新。
7. `UC08-F07` 系统将与该订单绑定的券更新为 `USED`。

### 6.3 主成功流程 B：团购券购买与核销

1. `UC08-F08` 用户浏览 `ON_SALE` 团购并进入团购详情。
2. `UC08-F09` 用户发起购买，系统创建 `PENDING_PAYMENT` 团购订单和待支付通知。
3. `UC08-F10` 用户进入支付页并完成模拟支付。
4. `UC08-F11` 系统条件扣减团购库存，生成唯一 `CLAS-` 正式券码和过期时间，将状态改为 `UNUSED`。
5. `UC08-F12` 系统发送购买成功通知，用户在团购订单详情查看券码。
6. `UC08-F13` 商家在工作台输入券码发起核销。
7. `UC08-F14` 系统校验券归属、状态和有效期，将状态改为 `USED` 并记录使用时间。
8. `UC08-F15` 系统写入核销日志并向用户发送核销成功通知。

### 6.4 备选或异常流程

| 编号 | 条件 | 系统处理 |
| --- | --- | --- |
| `UC08-A01` | 用户重复领取同一普通券 | 拒绝领取 |
| `UC08-A02` | 普通券总量已满、失效或过期 | 不展示或拒绝领取/使用 |
| `UC08-A03` | 普通券不适用当前商家 | 拒绝抵扣 |
| `UC08-A04` | 订单金额未达到用券门槛 | 拒绝抵扣 |
| `UC08-A05` | 普通订单取消或超时 | 将 RESERVED 券释放回 UNUSED并清除订单绑定 |
| `UC08-A06` | 团购下架 | 拒绝购买或支付 |
| `UC08-A07` | 商家手动打烊或不在营业时间 | 拒绝购买 |
| `UC08-A08` | 团购库存不足 | 拒绝支付完成，不产生可用券 |
| `UC08-A09` | 使用 FAIL_MOCK 模拟支付 | 返回失败，保持 PENDING_PAYMENT，不扣库存 |
| `UC08-A10` | 券码不存在或属于其他商家 | 拒绝核销 |
| `UC08-A11` | 券已使用、退款、失效或过期 | 拒绝核销 |
| `UC08-A12` | 用户对未使用且未过期的券退款 | 恢复团购库存，状态改为 REFUNDED并通知用户 |
| `UC08-A13` | 用户对已使用/已过期/已退款券退款 | 拒绝退款 |

### 6.5 可验证结果

- `UC08-V01` 同一用户同一普通优惠券最多一张，限量领取不会超发。
- `UC08-V02` 普通券的 `order_id`、`RESERVED`/`USED` 状态与订单一致。
- `UC08-V03` 支付失败不形成已支付结果、不使用普通券且不错误扣减库存。
- `UC08-V04` 团购支付成功只扣减一次库存，并生成唯一正式券码和过期时间。
- `UC08-V05` 只有券所属商家能够核销，成功核销只能发生一次。
- `UC08-V06` 成功核销存在一条包含订单、商家、券码、操作人和时间的日志。
- `UC08-V07` 团购待支付、购买成功、核销和退款通知均指向对应团购订单。

### 6.6 关联需求

`REQ-UC08-01`～`REQ-UC08-06`。
