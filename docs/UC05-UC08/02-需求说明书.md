## 1. 引言

### 1.1 目的

本文档定义 UC05–UC08 的功能需求、接口约束、数据要求、权限要求和验收标准，为概要设计、详细设计、代码核对和测试设计提供统一依据。

### 1.2 范围

- UC05：用户收藏商家、接收和管理业务通知。
- UC06：商家入驻申请、管理员审核和开店状态管理。
- UC07：商家维护店铺资料、商品分类、商品和经营状态。
- UC08：普通优惠券参与订单，以及团购券购买、支付、核销、过期和退款。

不包含真实支付渠道、实时推送、人工资质文件识别及本轮测试执行。

## 2. 总体说明

### 2.1 产品环境

CLAS 为前后端分离系统：前端使用 Vue 3、Vue Router、Axios 和 Element Plus；后端使用 Spring Boot 3、MyBatis Plus、MySQL、Redis；身份认证使用 JWT Bearer Token；支付为模拟支付。

### 2.2 用户特征

| 角色 | 主要能力 | 权限边界 |
| --- | --- | --- |
| USER | 收藏、通知、领券、下单、购买团购券 | 只能操作本人数据 |
| MERCHANT | 店铺/商品管理、团购核销 | 只能操作绑定店铺及该店业务数据 |
| ADMIN | 商家审核与状态维护 | 可查看全量商家审核信息 |

### 2.3 公共业务规则

1. 所有私有 API 必须鉴权；无认证返回 401，无角色权限返回 403。
2. 当前用户和当前商家由后端认证上下文解析。
3. 所有业务响应使用统一 `Result` 结构。
4. 金额使用整数“分”。
5. 业务失败必须保持所有权隔离和关键交易状态一致。
6. 测试未执行前，不得把需求标记为“验证通过”。

## 3. 功能需求

### 3.1 UC05 收藏与通知需求

#### REQ-UC05-01 收藏关系唯一性与所有权

系统必须仅允许 USER 管理本人收藏，并保证同一用户和同一商家最多存在一个收藏关系。

验收标准：

- 首次收藏有效商家时创建收藏记录。
- 重复收藏返回已有关系，不新增重复记录。
- 收藏不存在的商家返回业务错误。
- 收藏数据以当前认证用户为归属。

#### REQ-UC05-02 收藏查询与取消

系统必须允许用户查看和取消自己的商家收藏。

验收标准：

- 收藏列表不包含其他用户数据。
- 取消收藏不影响其他用户对同一商家的收藏。
- 取消不存在的收藏保持幂等。

#### REQ-UC05-03 业务通知创建与排序

系统必须将订单、团购、预约、评价等关键业务事件保存为指定接收人的通知，并按未读优先、时间倒序展示。

通知至少包含：接收人、标题、正文、是否已读、业务类型、目标类型、目标标识和站内目标路径；特定业务应包含订单、商家、评价或回复标识。

#### REQ-UC05-04 通知生命周期和所有权

系统必须支持本人通知的单条已读、全部已读、单条删除和全部清空，并阻止用户修改或删除他人通知。

#### REQ-UC05-05 通知安全跳转与历史兼容

客户端必须仅对已支持的业务类型和受控站内路径进行跳转。历史通知只有在目标存在且与接收人匹配时才能回填结构化目标。

### 3.2 UC06 入驻与审核需求

#### REQ-UC06-01 申请人账号处理

系统必须支持以下申请方式：

- 游客通过账号手机号验证码、展示名和密码创建或复用账号后申请。
- 已登录用户沿用当前账号申请。
- 普通 USER 成功申请时升级为 MERCHANT。

游客密码必须满足系统密码规则，确认密码必须一致；既有账号必须密码正确且未被禁用。

#### REQ-UC06-02 入驻资料和唯一性

系统必须校验：

- 一个用户只能绑定一个商家。
- 商家名称唯一。
- 商家联系电话唯一且格式合法。
- 必须选择合法地图坐标。
- 店名、分类、地址等必填信息符合请求校验。

成功申请必须创建 `PENDING`、`manualClosed=false` 的商家。

#### REQ-UC06-03 审核授权和状态机

仅 ADMIN 可以审核商家。允许的状态转换如下：

```text
PENDING  -> APPROVED | BLOCKED
APPROVED -> OPEN | CLOSED | BLOCKED
OPEN     -> CLOSED | BLOCKED
CLOSED   -> OPEN | BLOCKED
BLOCKED  -> APPROVED | CLOSED | OPEN
```

同状态更新可用于补充管理员备注。非法转换必须被拒绝。

#### REQ-UC06-04 审核日志和进度可见性

每次成功审核必须记录商家、管理员、旧状态、新状态、备注和时间。商家申请人必须能查看当前状态、管理员备注和本人商家的审核时间线。

### 3.3 UC07 店铺与商品管理需求

#### REQ-UC07-01 当前商家归属

系统必须从当前 MERCHANT 账号解析绑定商家，并使用该商家 ID 限定店铺、分类和商品写操作。未绑定商家的账号不得执行商家管理。

#### REQ-UC07-02 店铺资料安全更新

系统必须支持修改店名、地址、地图坐标、配送范围、营业时间、联系电话和结算账号等资料，并满足：

- 地图坐标必须存在。
- 配送范围为 500～10000 米。
- 营业时间格式为 `HH:mm-HH:mm`。
- 联系电话变化时校验新电话验证码。
- 银行账号变化时校验原联系电话收到的验证码，且账号为 9～25 位数字。
- 新联系电话不能被其他商家占用。

#### REQ-UC07-03 手动经营状态

仅平台状态为 `OPEN` 的商家可以切换 `manualClosed`。交易入口必须识别手动打烊和营业时间，阻止当前不可营业商家的购买行为。

#### REQ-UC07-04 商品分类生命周期

系统必须允许商家创建、修改、排序和删除本店分类。同一店铺分类名称必须唯一。删除分类时必须保留商品，并把相关商品转为未分类。

#### REQ-UC07-05 商品生命周期与展示隔离

系统必须支持：

- 创建商品，初始状态为 `ON_SALE`。
- 修改本店商品资料和本店分类。
- 在 `ON_SALE` 与 `OFF_SALE` 间切换。
- 将商品软删除为 `DELETED`。
- 商家管理查询排除 `DELETED`。
- 用户商品查询仅返回 `ON_SALE`，分组查询不返回空分组。
- 商品或状态变化后刷新商家人均价格。

### 3.4 UC08 优惠券与团购券需求

#### REQ-UC08-01 普通优惠券领取

系统必须只展示有效、未领取且未达到总量上限的优惠券。领取时必须原子增加已领取数量并创建 `UNUSED` 用户券，防止重复领取和限量券超发。

#### REQ-UC08-02 普通优惠券结算生命周期

系统必须校验用户券所有权、状态、有效期、适用商家和最低金额，并按以下规则流转：

```text
UNUSED -> RESERVED：创建订单并绑定 order_id
RESERVED -> UNUSED：订单取消或超时，清除绑定
RESERVED -> USED：绑定订单支付成功
UNUSED -> EXPIRED：有效期结束
```

#### REQ-UC08-03 团购订单创建与支付

系统必须仅允许购买 `ON_SALE`、所属商家可营业且有库存的团购。购买时创建 `PENDING_PAYMENT` 团购订单；支付成功时条件扣减库存、生成唯一正式券码、设置有效期并转为 `UNUSED`。

模拟失败必须保持 `PENDING_PAYMENT` 且不得扣减库存。

#### REQ-UC08-04 团购券核销

只有券所属商家可以核销状态为 `UNUSED` 且未过期的券。成功核销必须更新为 `USED`、记录使用时间、写入核销日志并通知用户。重复、跨店、无效和过期核销必须失败。

#### REQ-UC08-05 团购券过期与退款

查询到超过有效期的 `UNUSED` 券时，系统必须更新为 `EXPIRED`。仅本人未使用且未过期的团购券可以退款；退款后恢复库存并转为 `REFUNDED`。

#### REQ-UC08-06 团购状态通知

团购订单进入待支付、购买成功、已核销或已退款状态时，系统必须向用户发送结构化通知，并指向 `/deal-order/{id}`。

## 6. 非功能需求

### NFR-01 安全性

- JWT 认证和角色授权必须覆盖私有接口。
- 用户/商家资源必须执行所有权校验。
- 通知跳转必须限制为受控站内路径。
- 密码不得明文保存；敏感资料变化必须验证码确认。

### NFR-02 一致性

- 入驻账号与商家创建、商家审核与日志写入必须保持事务一致。
- 限量领券、券预占/使用、普通订单支付、团购库存扣减和核销必须避免部分成功。
- 失败操作不得留下与订单不匹配的券状态。

### NFR-03 可审计性

- 审核和团购核销必须保留操作主体、对象、前后状态/结果与时间。
- API 响应应携带请求追踪标识，以便联调定位。

### NFR-04 可用性与兼容性

- 重复收藏、取消不存在收藏等适合幂等的操作不应产生重复数据。
- 历史通知目标允许安全回填，但不得因无法解析而错误跳转。
- 通知失败不得在规定场景中阻断已完成的团购核心交易。

### NFR-05 可测试性与追溯性

每条 `REQ-UCxx-yy` 必须至少映射到一个设计项、代码符号和测试编号。测试状态必须区分“已有但未复跑”“待实现”“已执行通过/失败”。
