# CLAS 微服务拆分现状与缺口

> 检查基线：`main` 分支提交 `50016ee9`（2026-09-01）。
>
> 本文以当前已提交工程为事实来源，对照小学期后五天“至少三个业务微服务、数据隔离、网关、独立部署与测试证据”的要求列出状态和缺口，不将尚未验证的能力表述为已完成。

## 3. 必须补齐的缺口与问题

### 3.1 数据隔离尚未实现

- 四服务的 `application.yml` 均使用同一个 `MYSQL_DATABASE=clas`。
- `clas-order` 仍直接包含并使用 `UserMapper`、`UserRoleMapper`、`CartMapper` 等跨领域数据访问；其它服务也复制了多个非本领域实体和 Mapper。
- 因此当前是“多进程 + 共享数据库/复制代码”的迁移形态，尚不满足“每张迁移表只有一个服务写入、禁止跨服务直接读写表或联表”的验收条件。

**需要补齐：** 明确表 owner，拆分为私有 schema 或私有数据库；将跨域查询、认证和写操作改为受控内部 API 或事件，删除跨服务 Mapper。

### 3.2 商家服务未独立存在，任务边界与实际模块不一致

- 看板中的商家服务任务要求独立拆分商家入驻、审核、资料和营业状态。
- 当前 `clas-catalog` 同时承担商家、商品、预约和团购发布；仓库没有独立的 `clas-merchant` 模块。
- `services/catalog-service/` 与 `services/clas-catalog/` 并存，前者还拥有 Dockerfile 和单测，后者是主路径实际使用模块，命名和实现存在重复。

**需要补齐：** 决定并记录最终边界：要么拆出独立商家服务，要么正式调整看板/设计中的服务边界和验收口径；同时淘汰或明确旧 `catalog-service` 的用途，避免部署到非主路径实现。

### 3.3 网关仅完成静态路由，韧性和发现能力缺失

- 当前网关是 Nginx，目标地址固定为 `127.0.0.1:8081` 至 `8084`，未实现注册中心或基于 Kubernetes DNS 的动态服务发现说明。
- 配置只透传已有的 `X-Request-Id`，没有在缺失时生成请求 ID，也未见统一的响应回写和跨服务日志关联验证。
- 未配置 `proxy_connect_timeout`、`proxy_read_timeout`、`limit_req`、熔断或降级；下游失败时只会得到 Nginx 默认的失败行为，未形成规定的用户可见响应和排查记录。
- JWT 由各业务服务分别校验，网关没有统一拒绝无效令牌的实现。

**需要补齐：** 在网关配置请求 ID 生成/透传/响应、连接与读取超时、限流，以及下游不可用时的受控 `503` 响应；确定服务发现方案并完成一次故障注入与恢复记录。

### 3.4 容器、Kubernetes 和 CI/CD 未覆盖新四服务

- 仅旧目录 `services/catalog-service/Dockerfile` 与 `k8s/catalog-service.yaml` 存在容器/部署资产。
- `clas-iam`、`clas-catalog`、`clas-order`、`clas-compat` 均没有各自 Dockerfile 和 Kubernetes Deployment/Service 清单。
- 现有主路径启动依赖本机 Java 进程和可选本机 Nginx；没有四服务的 Compose 编排。
- 启动脚本执行 `mvn package -DskipTests`，不能作为“测试失败阻断发布”的证据。

**需要补齐：** 为实际四服务模块创建版本化镜像、Compose、Kubernetes 清单、就绪/存活探针和服务级 CI；构建或测试失败必须阻断镜像发布与部署。

### 3.5 自动化测试与验收证据不足

- 新的 `clas-iam`、`clas-catalog`、`clas-order`、`clas-compat` 目录没有 `src/test` 测试代码。
- `services/catalog-service/` 有测试，但它不是四服务主路径的 `clas-catalog` 模块，不能代替主路径服务回归。
- 主路径冒烟脚本只覆盖有限查询和登录场景，未覆盖订单创建/退款、重复请求、越权、非法状态跃迁、下游超时或网关限流。

**需要补齐：** 为每个实际服务补单元/集成测试；为网关与订单主流程补 API、端到端和故障测试；保存总数、通过/失败、环境、日志与受控失败记录。

### 3.6 文档与部署资产已经过期或相互冲突

- `docs/microservice-design.md` 仍称“商品目录服务已独立实现，其余领域仍处于单体迁移阶段”，并指向 `services/catalog-service`，与当前四服务结构不一致。
- `k8s/catalog-service.yaml` 和旧 Dockerfile 指向旧目录，不能证明最新 `clas-*` 服务已经部署。
- 现有服务划分文档中的目标服务数量、表归属和接口边界，尚未与四模块真实代码和看板任务逐项对齐。

**需要补齐：** 以 `services/clas-*` 为唯一当前实现更新服务划分图、接口清单、表归属、部署与回退说明；将旧 `catalog-service` 标为迁移原型或移除其部署入口。

## 4. 建议的处理顺序

1. 先冻结四模块的最终职责和表 owner，决定是否从 `clas-catalog` 拆出商家服务。
2. 以 `clas-order` 为起点移除跨域 Mapper，先完成订单—目录—身份的内部 API 与契约测试。
3. 补网关请求 ID、超时、限流和下游故障响应，并保留故障演示证据。
4. 为真实 `clas-*` 模块补测试、Dockerfile、Compose、Kubernetes 和 CI/CD；不再以旧 `catalog-service` 资产作为四服务验收证据。
5. 更新设计文档、看板状态和 PR 证据，只将已运行、已记录的结果标记为完成。
